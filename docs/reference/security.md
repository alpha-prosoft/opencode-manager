# Security model

This page is for security reviewers and platform operators. It describes what the platform protects, the controls it uses, and what you must provide for those controls to hold. The checklist to go through before going live is in [Govern and operate](../story/operate.md).

## What is protected from what

The platform runs AI agents that execute commands and read files. The design assumes an agent may be misled by what it reads (a prompt injection in a repository or a ticket) and will then try whatever its sandbox permits. The controls therefore don't rely on the agent behaving:

| Asset | Protected by |
|---|---|
| LLM keys, Git tokens, tool credentials | They never enter a sandbox. Gateways add them on the platform side. |
| Other tenants' data | Every request works inside the caller's tenant. |
| Your network and the internet | Sandboxes run on a network with no route out. |
| Repositories and pull requests | Agents return typed results; the platform decides what is pushed or posted. |
| The record of what happened | The audit trail is written outside the sandbox and hash-chained. |
| Spend | The LLM gateway meters every call and enforces team budgets. |

## The two listeners

The manager listens on two ports that share no routes.

| Listener | Default port | Serves | Must be reachable by |
|---|---|---|---|
| Public | 8000 | UI, API, login, webhook endpoint, session access checks (forward auth), `/metrics`, audit export | The HTTP router (Traefik) only |
| Sandbox | 8001 | LLM gateway, MCP gateway, result tools, telemetry | Sessions only |

On the compose stack the two are bound to different Docker networks. Traefik joins the sandbox network to reach session containers but listens only on its public network address, so a session can't reach the public listener through it either. On Kubernetes the sandbox listener has its own Service that no route exposes, and the chart's three NetworkPolicies enforce who reaches which port: session pods accept traffic only from the manager and the gateway and may send only to the manager's port 8001 and DNS; sessions of an `internet` harness may also reach any address outside `networkPolicies.internetExcept`; the manager accepts port 8000 only from the gateway and port 8001 only from session pods.

Both listeners limit request bodies (`MANAGER_MAX_BODY_BYTES`) and read times.

## Sandbox isolation

**Network.** Sessions run on an internal network with no route to the internet or to your other systems. A session reaches only the manager's sandbox listener. A harness with `"network": "internet"` opts its sessions into outbound internet access; on Kubernetes such sessions are still kept away from the address ranges in `networkPolicies.internetExcept` (the private ranges by default), so they can't reach in-cluster services such as MCP servers directly.

**Container.** A session runs as a non-root user (uid 1000) with a read-only root filesystem (only the workspace and `/tmp` are writable), all Linux capabilities dropped, no privilege escalation, and CPU, memory and process limits from its harness. On Kubernetes it also has the `RuntimeDefault` seccomp profile and no service account token.

**Configuration.** The OpenCode configuration (model, provider, permissions, MCP servers, skills) is generated by the platform from the harness and mounted read-only. OpenCode's project-level configuration, default plugins and external skills are switched off for the session. The agent can't change its own model, permissions or tools.

**Policy.** A platform plugin inside that read-only configuration enforces the harness's `policy` (denied commands and paths) before a tool runs and reports tool calls. The agent can't disable it.

**Images.** A harness may use only images listed in the tenant's `allowed_images`.

## No credentials in sessions

LLM API keys, Git tokens, SCM tokens and MCP credentials, shared or personal, stay in the manager.

A session authenticates to the LLM gateway, the MCP gateway and the result tools with **per-session keys** derived from the platform's signing key. A session key works only for its own session, the models and MCP servers of its harness, and the result tool of its run.

### LLM gateway

- Adds the real provider credential to each request.
- Refuses models that are not in the session's harness (*Model … is not allowed for this session*).
- Enforces the team's daily token budget (answers `429`).
- Records prompt, completion and cached tokens, latency and errors from the provider's answer.

### MCP gateway

- Refuses servers the session's harness doesn't list.
- Hides tools outside the server's `tools` allow-list and refuses calls to them.
- Chooses the credential value (the owner's own, the team's, the tenant's; see [Credentials](credentials.md)) and adds it to the request. The value is sent only to hosts listed for the credential.
- Writes every tool call to the session's audit trail, with which kind of value was used.

### Git and SCM

Checkouts, pushes, pull requests and review comments are done by the manager, not by the agent. A secret used for Git is sent only to the hosts listed for it (`hosts` of the credential, `secret_hosts`). Plain `http://` Git URLs are refused unless the operator lists the host in `MANAGER_HTTP_GIT_HOSTS`. `file://` repositories must be under `MANAGER_LOCAL_REPO_ROOTS`. Files that definitions refer to can't be outside the team's definitions directory, not even through symbolic links.

## Controlled side effects

Automated activities end with the agent calling a typed result tool. The platform validates the submission and decides what happens:

- A review becomes at most `max_comments` comments, anchored only to lines that are in the diff, and is posted only in `auto` mode.
- An implementation's patch is computed by the platform from the working tree. If the workflow delivers changes, the platform commits, pushes a new branch and opens a pull request. Nothing is merged. Unverified work is opened as a draft.
- Harness policies commonly deny `git push`, so the only way a change leaves the sandbox is through the platform.

## Personal credentials stay personal

- Only the owner can work in a session that uses their own credential values. Others fork it and continue with theirs.
- Team sessions use the team's values, so only members of that team (and tenant admins) can work in them, however widely they are shared.
- A required credential can be satisfied only by the person's own value, so actions in that tool are attributable to a person.

## Stored secrets

- Credential values and webhook secrets are **sealed at the edge**: the public listener encrypts a value, bound to what it belongs to and its owner, before it sends the command. The platform keeps a log of commands, and a plaintext secret in it would be a leak; so plaintext never gets that far.
- Encryption is AES-GCM under `MANAGER_CREDENTIALS_KEY`.
- A value is never returned by the API; only a short hint is.
- Operator secrets are files or environment variables read only by the manager.

## Browser and session access

**Sign-in.** In oidc mode the manager runs the authorization code flow with PKCE, state and nonce, verifies the ID token (signature, issuer, audience, nonce, expiry) and issues its own login cookie. In jwt mode it verifies the token on every request. A signing key verifies only tokens of its own algorithm; a token whose header names another algorithm is refused. Unusable default algorithms (`none`, HMAC) stop the manager at start.

**Login cookie.** The cookie (`oc_auth`) is always host-only on the manager's domain, `HttpOnly` and `SameSite=Lax`, so session host names (`<session>.<domain>`) never receive it. Over https it is also `Secure` and named `__Host-oc_auth`, which keeps session subdomains from setting or shadowing it.

**Opening a session.** The UI hands the browser over with a one-time token that is valid for 60 seconds and bound to the session. The session's host then gets its own short-lived cookie, valid only for that session and only for the access check. The router asks the manager before every request to a session (a forward-auth middleware) and a second middleware empties the `Cookie` header before the request reaches the sandbox. Both are part of every session route, on compose (the Traefik file the manager writes) and on Kubernetes (the chart's two Middlewares).

**CSRF rule.** The public listener refuses a state-changing request that carries cookies unless it comes from the UI's origin: `Sec-Fetch-Site: same-origin`, a matching `Origin`, or the `X-Requested-With` header the UI sends. Scripts that call the API with a cookie must send `X-Requested-With`.

**Content-Security-Policy.** The UI is served with:

```text
default-src 'self'; script-src 'self' '<hash of the one inline script>'; img-src 'self' data:;
style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'
```

and `X-Frame-Options: DENY`. `MANAGER_CONTENT_SECURITY_POLICY` replaces the policy and `off` removes it; both exist for UI development only.

**Error messages.** What people read of a failure is a message the platform wrote itself. Any other error is logged and shown as a fixed sentence, because its text may name server paths or internal hosts.

## Tenant isolation and access control

- Every query and command works within the caller's tenant, taken from their token. Another tenant's sessions, runs, credentials, usage, audit trails and admin views answer "not found".
- Inside a tenant, only a team's members and tenant admins see its workflows, runs and page. A session is seen by those it is shared with, plus the team's admins. See [Roles and visibility](roles.md).
- Operators administer the platform but see no tenant's data.
- Images, LLM connections, models, MCP servers and secrets must be granted in the tenant's `tenant.json` (and chosen in the team's `team.json`) before a team can use them. Violations are rejected at sync.

## Audit trail

For every running session the manager follows OpenCode's event stream, authenticated with the session's server password, and records messages, tool calls with inputs and outputs, and session events. Recording happens in the manager, outside the sandbox.

- **Append-only.** Entries are only ever added.
- **Hash-chained.** An entry's hash is the SHA-256 of the previous entry's hash, the timestamp, the type, the key and the body. The body is stored verbatim, so verification and export never depend on re-serialising it. Changing or removing an entry breaks every hash after it.
- **Verifiable.** The session's Audit trail tab recomputes the chain.
- **Exportable.** The whole trail downloads as JSONL.
- **Kept.** It survives the deletion of its session.

The Live activity view is a convenience built from the plugin's reports. The audit trail is the record.

## Webhooks

The webhook endpoint accepts calls without a login, so it has its own controls: a secret per webhook compared in constant time, optional HMAC signatures with a timestamp window, allowed source addresses, a rate limit that refused callers can't exhaust for the real one, indistinguishable 404s, and refusal reasons that are logged but never sent. The caller's address is taken from `X-Forwarded-For` only for proxies in `MANAGER_TRUSTED_PROXIES`. Details are in the [Webhooks reference](webhooks.md).

## What you must provide

The controls above depend on the environment:

| You provide | Otherwise |
|---|---|
| A network plugin that enforces NetworkPolicies (Kubernetes) | Session pods can reach the public listener and other services. |
| TLS at the gateway and `publicScheme: https` | Cookies are not marked `Secure` and lack the `__Host-` prefix. |
| An identity provider whose group and role claims you control | Anyone who can set those claims chooses their tenant and role. |
| Protection of the onboarding and team repositories | Whoever can push to them changes what agents may do. |
| Safe keeping of the credentials key and the database | Together they contain every stored credential. |
| A narrowed `trustedProxies` | A caller inside the trusted ranges can claim any source address. |
| The test login turned off (`MANAGER_AUTH_MODE` is not `login`) | Anyone can sign in as anyone. |

The repository's end-to-end test suite probes these controls from inside a real session.
